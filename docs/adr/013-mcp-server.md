# ADR 013 — The Trustwork MCP server

Date: 2026-10-31. Status: **Proposed** (architect: Claude, an AI agent working for the repository owner Dmitry Parshkov, on the owner's request of 2026-10-31). Nothing here is implemented; the design is [The MCP server](../engine/mcp-server.md), the contracts are [`packages/contracts/src/mcp.ts`](../../packages/contracts/src/mcp.ts) (status **Contract** once merged) and the work is MCP-001 … MCP-090 with AGT-016 as the acceptance umbrella in [work-packages.json](../engine/work-packages.json). Requirement R54.

## Context

The owner asked (2026-10-31): *design the full architecture of the project's MCP server, so that every user can use it for their own purposes: authenticate and use the whole system from their own AI chat.* The same day the owner clarified (ADR 010 decision 23): everything revolves around the person's own agent, their representative; **every participant-facing capability exists both through that agent and directly in the interface**, through one capability registry, with a parity report in CI; commitments still need a confirmed mandate, a budget where money is involved and the person's confirmation.

The starting point was the agent catalogue's section [Connect your own agent](../engine/agent-catalog.md#connect-your-own-agent-mcp-and-a2a): a connection is another hand of the person's one agent; OAuth 2.1 with PKCE; audience-bound short-lived tokens stored as hashes; cookies never authorize MCP; it acts only inside mandates confirmed on the site; private data is opt-in per class; it never approves, creates or widens mandates or presses kill switches; audit, rate limits, circuit breaker and revocation. This ADR keeps all of that and makes it concrete against the protocol as it stands today.

### What the protocol looks like on 2026-10-31

Verified against the specification (sources at the end, accessed 2026-10-31):

- The current revision is **2026-07-28**. It removed the `initialize` handshake and protocol-level sessions: every request carries its protocol version and client capabilities in `_meta`, servers implement `server/discover`, and state that spans calls lives in explicit server-minted handles passed as tool arguments. Streamable HTTP is one POST endpoint answering with JSON or a request-scoped SSE stream; it requires the `MCP-Protocol-Version`, `Mcp-Method` and `Mcp-Name` headers and rejects header/body mismatches. Server-to-client requests (elicitation) now travel as an `InputRequiredResult` that the client answers by retrying the original request with `inputResponses` and the opaque `requestState` (multi round-trip requests). List results carry `ttlMs` and `cacheScope`. Tasks moved into an official extension (`io.modelcontextprotocol/tasks`, Beta). Roots, Sampling and Logging are deprecated.
- **Authorization** is OAuth 2.1: the MCP server is a resource server that MUST publish Protected Resource Metadata (RFC 9728); the authorization server publishes RFC 8414 or OpenID Connect discovery metadata; clients MUST send resource indicators (RFC 8707) and servers MUST validate the token audience and MUST NOT accept or pass through other tokens; PKCE S256; `iss` in authorization responses (RFC 9207) is recommended and validated by clients; step-up through `403 insufficient_scope` challenges. Client registration prefers **Client ID Metadata Documents**; Dynamic Client Registration is deprecated but kept for compatibility.
- **Elicitation** has a form mode and a **URL mode** for interactions that must not pass through the client; servers MUST NOT use form mode for secrets or payment credentials, MUST NOT put personal data or pre-authenticated links into the URL, and MUST verify that the person who opens the URL is the person the request was for.
- **Clients today.** Claude (web, desktop, mobile, Cowork, Claude Code) connects to remote servers over OAuth, supports CIMD (only when the authorization server advertises `client_id_metadata_document_supported` and the `none` token endpoint method) and falls back to DCR, needs a `401` with a `resource_metadata` pointer, uses the first listed authorization server, and redirects to `https://claude.ai/api/mcp/auth_callback` or a loopback URI for Claude Code. ChatGPT (developer mode and apps) connects to remote servers over OAuth with PKCE S256, prefers CIMD, falls back to DCR, sends `resource` on both requests and redirects to `https://chatgpt.com/connector_platform_oauth_redirect` when the `iss` rules are met. **Uncertain:** which clients already speak 2026-07-28 rather than 2025-11-25, and which render URL-mode elicitation; the public extension matrix did not show this reliably. The design therefore keeps a fallback for both.

## Decisions

1. **Parity first: the MCP catalogue is a projection of the capability registry.** There is one registry of capabilities, derived from the contracts, that the person's built-in agent, the MCP connection and the interface all use (ADR 010 decision 23): AGT-002's `AgentCapabilitySchema` in [`agent-catalog.ts`](../../packages/contracts/src/agent-catalog.ts), with kind, contract-derived input and output, read layers, private data classes, mandate kind, confirmation, budget kind, side effects, meters and surfaces (`ui`, `agent`, `mcp`, `a2a`). Every MCP tool is a projection of exactly one registry capability (`McpToolSchema` in [`mcp.ts`](../../packages/contracts/src/mcp.ts)) and adds only what MCP needs: a stable tool name `<toolset>_<operation>`, toolset, model-facing title and description, annotations, the endpoints it appears on and the private classes it redacts. Scopes come from the registry (`requiredConnectionScopes`) and so does the decision to execute, ask or deny (`connectionMayInvoke`). A capability missing the `ui` or `agent` surface is a parity gap (`parityGaps`), a capability with the `mcp` surface without exactly one tool is a coverage gap (`mcpProjectionGaps`), and the CI **parity report** lists both (MCP-001). The catalogue covers every participant-facing module; the only steps that do not execute over MCP are the ones the rules reserve for the person on the site, and even those exist as **handoff** tools that open the exact first-party page ([exclusions](../engine/mcp-server.md#what-never-executes-over-mcp-and-why)).

2. **Registry kinds and handoffs.** The registry's kinds are `read` (no change), `draft` (inert, owner-private), `commit` (shared state under a mandate) and `govern` (the person's own authority: confirm or revoke mandates, approve decisions, the stop control, consent to a connection), which no connection can ever reach. MCP adds **handoff tools**: read-only tools that return the link to the first-party form of a `govern` capability, or to another first-party-only page (security, privacy, legal acts, reviews, large uploads); they invoke nothing. The contract enforces that nothing is both read-only and committing, that every commit names a mandate kind and a confirmation (`mandate`, `person_each` or `person_each_step_up`), and that governance is reachable only through a handoff.

3. **Three surfaces per hub, one endpoint each.** Every hub serves, on its own origin, `/mcp` for signed-in participants, `/mcp/public` for anonymous read-only access to public projections, and `/mcp/admin` for hub staff. Each is its own protected resource with its own canonical URI (the token audience), metadata and rate limits. Alternatives rejected: **one endpoint per participant** (identity in the URL, leaks in logs and links, breaks client directories and CIMD, and is unnecessary because the token identifies the person); **one endpoint per node** serving several hubs (hubs differ in enabled modules, prices, jurisdiction settings, languages and disclosure wording, and a token must be audience-bound to exactly one hub's policy); **mixing staff and participant tools on one endpoint** (a participant token could then be stepped up into staff power, and tool lists would leak the staff surface). The admin surface is **off by default** in every hub.

4. **Streamable HTTP only, pinned to 2026-07-28, with a compatibility window.** No stdio server (a hub is remote by nature) and no deprecated HTTP+SSE transport. The server implements the 2026-07-28 stateless protocol (`server/discover`, per-request `_meta`, header validation, `Origin` validation) and, during the deprecation window and while major clients still use it, the 2025-11-25 handshake on the same endpoint; it never mints `Mcp-Session-Id`. Cross-call state (drafts, confirmations, long jobs) lives in opaque handles bound server-side to the person and the connection; possession of a handle is never authentication.

5. **The node runs its own authorization server for its hubs.** Issuer = the hub origin; the person signs in with the same first-party login (and second factor where enrolled, BE-004). Published: RFC 9728 metadata at `/.well-known/oauth-protected-resource/mcp` (and per surface), RFC 8414 metadata, `code_challenge_methods_supported: ["S256"]`, `authorization_response_iss_parameter_supported: true` with `iss` on every response, `token_endpoint_auth_methods_supported: ["none", "private_key_jwt"]`, `client_id_metadata_document_supported: true`, a revocation endpoint (RFC 7009). The `resource` parameter is required and must equal one of the hub's three canonical URIs. Alternative rejected: delegating to an external identity provider (the engine already owns identity, step-up and recovery, and an external provider would add a dependency that every hub operator must configure and trust).

6. **Client registration.** Client ID Metadata Documents are preferred and fetched through the egress proxy with SSRF protections (HTTPS only, private and link-local ranges blocked, size and time limits, cache by HTTP headers). Pre-registration exists for company systems connected to the standing representative (confidential, `private_key_jwt`). Dynamic Client Registration stays available behind a hub switch (on by default because some clients still fall back to it), rate-limited, with unused registrations garbage-collected. A client's name is always shown as **self-asserted** unless the hub listed the client; listing is informational and never grants scope.

7. **Tokens.** Opaque access tokens, at most 15 minutes, stored only as hashes, audience-bound to one surface's canonical URI; rotating refresh tokens with reuse detection that revokes the whole family; absolute and idle lifetimes set by the hub within engine bounds; sender-constrained (DPoP, RFC 9449) when the client supports it. A token references the **connection** (AGT-002's `ExternalConnection` with protocol `mcp`, plus `McpConnectionDetails`); scopes, toolsets, private data classes and mandate bindings are looked up server-side on every call, so revoking or narrowing takes effect before the next call. Session cookies never authorize MCP, and MCP tokens never authorize the first-party web API.

8. **No token passthrough, ever.** The MCP server never forwards the client's token or accepts a token issued for another resource. When a tool needs a provider (model, register, payment, e-signature), the hub's own provider connections are used through adapters under the egress matrix; when a deal reaches another node, the home node acts under federation rules with its node signature. Third-party authorization a person must give (for example linking a calendar) uses URL-mode elicitation to a page on the hub origin, never the MCP client.

9. **Consent per client, on the hub's own page.** After step-up, the consent screen shows the client name (self-asserted or listed), the client id host and redirect host (with a warning when only loopback redirects are registered), the requested scopes in plain language, the **toolsets** (domains) the client will see, the private data classes (AGT-002's `PrivateDataClassSchema`) all off and opted in one by one with a residency warning, optional mandate bindings by id and revision (required for `act`), the expiry and the rate limits. It is CSRF-protected and cannot be framed. Consent is stored per person and client; a changed redirect URI or client id requires new consent. Scopes are requested progressively: the initial grant is `read.public read.me`; tools beyond it answer `403 insufficient_scope` with the exact scopes, and the client steps up.

10. **Commitments are confirmed on the site; chat text never authorizes.** A commit executes at once only when the connection holds `act`, a mandate bound to it pre-authorizes the action within limits and budgets (the mandate itself was confirmed on the site) and `evaluateMandateV2` allows it. Otherwise the action lands in the person's decisions (`connectionMayInvoke` → `propose_only`) and the server creates a **confirmation challenge** bound to the person, the connection, the capability version and the action digest, and returns a URL-mode elicitation to `https://<hub>/confirm/<id>`; the page renders the action from first-party records, never from model text, and the person confirms there after signing in. The client retries with the AEAD-protected `requestState`; the server consumes the challenge once and executes with the challenge as the idempotency key. Human-only verbs (`confirm_execution`, registry confirmation `person_each`) are confirmed on the site every time. For clients without URL-mode elicitation the same challenge is returned as a tool result with the link and appears in the person's decisions waiting. Unknown outcomes go to reconciliation, never to a blind retry.

11. **Annotations are explicit and honest.** Every tool sets all four hints (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`) instead of relying on protocol defaults; `openWorldHint` is true when the effect reaches other people or other systems. The hints help clients ask for confirmation; the server never relies on them.

12. **Untrusted content is marked in every result.** Every free-text field that came from another participant, another agent, a file, mail, a web page, an imported source or a federated peer is wrapped as `UntrustedText` (origin and source reference) in `structuredContent` and fenced and labelled in the text rendering; tool descriptions state that such text is data, not instructions. Addresses, amounts and counterparties found in untrusted text are never used for a commit without confirmation (`mcp.untrusted_value_needs_confirmation`).

13. **Data-class filtering at the serializer.** Tool output passes the same projection serializers as the web API for the person's audience, then a second filter by the connection's data classes: a capability that needs a private class the connection has not opted into is denied, and private fields a tool only redacts are removed and listed in `_meta.redactedFields`. Two further classes are proposed for AGT-002's enum (`contact_details`, `documents`); until added, those fields never reach a connection. Private data never reaches a client unless the person opted in for that class.

14. **Toolsets keep the catalogue usable.** The full participant catalogue is large; a connection sees only the domains ticked on the consent screen (default: account, agent, knowledge, notifications, hub, plus the domains of the person's active modules). The list changes only through the person's settings, and `notifications/tools/list_changed` is sent on the `subscriptions/listen` stream.

15. **Versioning and deprecation.** Tool names are stable and derived from capability ids (`plans.propose_version` → `plans_propose_version`; letters, digits and underscores, at most 64, which every major model API accepts). Compatible changes keep the name and raise the entry's version; breaking changes add a new capability; a deprecated tool carries its sunset date and replacement in `_meta` for at least 180 days. Protocol revisions follow the specification's deprecation windows.

16. **Federation: a person's client talks only to their home hub.** Tokens are valid only on the issuing hub. Public reads may show federated replicas labelled with their home hub; actions that involve a party on another node go through the home node, which applies [federation](../engine/federation.md) rules (deal routing, replicas, node signatures). A peer node can never authorize anything for the person.

17. **The admin surface is narrower than the console.** Staff tools read queues, cases (private content only under an active case grant), statistics (cohort-suppressed) and configuration, and draft decisions, summaries and configuration versions. There are no staff commits: every staff decision, second-person approval, case grant, kill switch, secret, provider, staff assignment, erasure and price activation happens in the console, reached by a handoff. Staff consent requires an elevated session.

18. **Localization and errors.** Tool names, descriptions and schemas are English (model-facing). Everything a person reads (elicitation messages, the consent and confirmation pages, `userMessage` in errors, labels in results) comes from locale files in the person's language. Errors are stable English codes: JSON-RPC and HTTP for protocol problems, tool execution errors with `mcp.*` or engine codes for business problems.

19. **Abuse and safety controls.** Token buckets per connection and tool class, commits counted per hour, the anti-scraping cap on public records, a circuit breaker that suspends a connection after repeated denials, loops or injection signatures, a `connection_call` audit row for every call (argument digest, not arguments), and the kill switches of the agent catalogue (`external_agent_api`, person stop, connection). Engaging a switch takes effect before the next call.

## Consequences

- AGT-016 becomes the acceptance umbrella of twenty packages (MCP-001 … MCP-090); AGT-017 (A2A) and AGT-019 (safety evaluation) keep depending on it.
- `mcp.ts` builds on AGT-002 (PR #197): it imports the registry, scopes, private data classes, connections and mandate verbs instead of defining its own, and requests two additions to `PrivateDataClassSchema` (`contact_details`, `documents`).
- Every module package that adds a participant-facing operation must add its registry entry, or the parity report fails.
- The hub console's External agents screen (HC-82) gains the MCP policy fields ([Agent product administration](../engine/hub-console/user-agents-admin.md#external-agents-mcp-and-a2a)).
- A participant guide explains how to connect: [Connect Trustwork to your AI chat](../guides/connect-your-ai-chat.md).

## Questions for the owner

1. **Admin surface.** Is a staff MCP surface wanted at all in the first release, or only after the console is complete (proposal: designed now, off by default, built after the participant surface)?
2. **Public surface answers.** Should anonymous clients get cited answers (`knowledge_ask`, which spends model and retrieval budget), or only search and records (proposal: search and records on, answers off by default, per-hub switch)?
3. **Dynamic registration.** Keep DCR on by default for compatibility with clients that fall back to it, or require CIMD (proposal: on by default, a hub can turn it off)?
4. **Listed clients.** Should the US reference hub list well-known clients (Claude, ChatGPT) by their metadata URLs so the consent screen can show them as listed (proposal: yes, informational only)?
5. **Pre-authorized commits.** May a mandate bound to a connection pre-authorize commits without per-action confirmation, as it can for the built-in agent (proposal: yes, within the same limits; human-only verbs and the exclusions never)?
