# ADR 014 — Sanctions compliance engine

Date: 2026-10-31. Status: **Proposed** (architect: Claude, an AI agent working for the repository owner Dmitry Parshkov, on the owner's request of 2026-10-31). The owner's decision that starts it is recorded as [ADR 010](010-gathering-point-hubs-agents-and-mesh.md) decision 24; the owner's decisions on enforcement of 2026-10-31 are recorded here (decisions 3 to 5). Nothing below is implemented except what the status table at the end calls Live. The design is the handbook chapter [Sanctions compliance](../engine/modules/sanctions-compliance.md); the data is [§24a of the data dictionary](../data/model.md#24a-sanctions-compliance); the work is SANC-001 … SANC-009 in [work-packages.json](../engine/work-packages.json). Requirement R72. Not legal advice: every rule that cites law below is for counsel to confirm before a hub relies on it.

## Context

The owner (2026-10-31): *"Our hub must have a full sanctions-compliance engine — the same as we have on Contribuda."*

Contribuda, the owner's other product, has a working engine (its ADR-0060, "No service in the places United States sanctions close", and the code that implements it). It was studied read-only from its repository's `main` on 2026-10-31. In short, Contribuda:

- keeps the restricted places as code with the law that closes each, with no setting, allowlist or staff exception;
- refuses every request from a restricted place at every door (each front's proxy and the core API), reading the place from the edge-written client address against a locally committed IP range table reduced to the restricted places (region-level for Ukraine), refreshed monthly, never storing or logging the address;
- **holds** a signed-in person seen in a restricted place: the hold refuses them on every request and at sign-in by name until an operator clears it with a reason; a second sighting keeps the first hold; cleared holds stay on record;
- screens every person's account names at every sign-in against OFAC's Sanctions List Service exports (SDN and the consolidated non-SDN lists, primary names and aliases) with deterministic name keys; a possible match is recorded, stops the person's money (payout onboarding and every withdrawal ask the core first and fail closed) and waits in an operators' queue until an administrator decides "not the same person" (with a reason) or "confirmed" (the person is suspended; the blocked-property report stays the operator's);
- re-screens everyone after a new list publication, keeps holds and screening records for ten years through a person's erasure (naming the tombstone), shows kind refusal words, and refuses a payout account in a restricted country before the payment provider is asked.

Trustwork today has the authoritative restricted-places list (`packages/country-packs/packs/restricted.json`) enforced in configuration, country packs, the database kernel (`kernel_place_restricted`, fail closed) and the console contracts; the ownership declaration with the 50% rule and a Consolidated Screening List adapter that refuses to run without a key and never fakes "clear" (`packages/compliance`, INTL-SAN); and designs that mention screening (HUB-003, [Hub administration](../engine/hub-administration.md#sanctions-screening-configuration), console screen HC-74). It has **no** visitor jurisdiction gate (the hosted preview relies on the hosting landing's place check in front of the private network), no holds, no ingested lists, no matcher, no review cases, no money gate and no re-screening. The reference hub is a United States deployment operated by Contribuda (ADR 010 decision 16, ADR 012 decisions 26 and 28), so it needs at least what Contribuda has; and Trustwork is an engine that other operators run for other countries, so everything country-specific must be configuration or an adapter (ADR 010 decisions 6 and 16).

## Decisions

### Scope and the line between the engine and what we control

1. **Full parity, configurable per hub.** Trustwork implements every capability of Contribuda's engine (parity table below) as one engine module, *sanctions compliance* (`SNC`), with three parts: the **jurisdiction gate** (restricted places, visitor geolocation, holds, self-declared places), **list screening** (lists, ingestion, matching, screening runs, review cases, re-screening) and **gates** (money, commercial commitments, agents, federation). What differs per hub is data or an adapter: which lists beyond the baseline, matching thresholds inside engine bounds, review service levels, geolocation adapter, record-keeping period and the wording a subject may be told. The guard rails are engine code and no console can switch them off (decision 16).

2. **Restricted places stay code and cover everyone.** The list in `restricted.json` remains the only source (the compliance package reads it, PR #314); lifting a place is a reviewed pull request with an ADR, never a setting. No allowlist, staff bypass, header, mandate, agent extension or hub setting lets a person in a restricted place through, the owner and the operators included (parity with Contribuda). A hub may **add** places its own law closes, through a versioned hub configuration with a cited legal basis and a second person; it can never remove a place.

3. **No self-detecting kill switch in the engine** (owner decision, 2026-10-31). Trustwork does not ship code that geolocates the server it runs on, phones home, or disables itself by location: it is trivially removed in a fork, unreliable, and erodes the trust an open engine depends on. The visitor gate of decision 6 is a different thing: it runs inside the operator's own deployment, under the operator's configuration, with a local dataset, and no address or decision leaves the server.

4. **Enforce on what we control** (owner decision, 2026-10-31):
   - **Our own services refuse restricted places**, using the node's declared jurisdiction and the operator's attested locations (decision 5) plus geolocation performed on **our** side of the connection: federation and mesh admission ([ADR 011](011-federation-mesh.md) decision 12, already refusing a manifest that declares a restricted place, now also refusing a node whose attested or observed location is restricted), the official update and release channel and container registry pulls, the public hub directory, project support and any service Contribuda hosts. A refusal is recorded with the place and the dataset, never the address. Work package SANC-008.
   - **Deployment-location attestation in the setup wizard**: the operator states the country of its legal entity and the hosting country (and region where the pack distinguishes regions); a restricted place is refused; the attestation is a signed, audited record and must be renewed when either location changes and at least yearly. It complements, not replaces, the refusals in configuration, packs and the database kernel. Work package SANC-009.
   - **Trademark.** Forks running in restricted places may not use the Trustwork name or mark: `NOTICE` reserves the marks ("the licence grants no right to use them to imply endorsement or origin of a modified version") and [BRAND.md](../oss/BRAND.md) records the brand rules; the explicit restricted-places wording in the brand policy is for counsel to confirm (open question 6).
   - **Publishing the open-source engine.** The export-control wording that accompanies publication (the informational notice in `NOTICE`, the classification of the published source as publicly available) must be confirmed by counsel; nothing in this ADR is that confirmation.

5. **The attestation and the gates are evidence, not a guarantee.** A VPN defeats an address check and an operator can lie in an attestation. The engine acts on what it knows (a sighting, a declaration, a list match) and keeps the record; it never claims more. Signals beside the address (stated residence, payment-instrument country from the provider, known hosting and VPN ranges) are later adapters (decision 7).

### The jurisdiction gate

6. **Every door refuses, first.** In front of anything else:
   - the web proxy (`apps/web/proxy.ts`): a page request from a restricted place renders the refusal page at `/restricted` in the visitor's language (HTTP 451 "Unavailable For Legal Reasons", RFC 7725, where the runtime allows a status on a rewrite, otherwise 200 with `noindex`); any other request (an API call through the same origin, a form post, a server action) is answered 451 with the error code `jurisdiction.restricted`;
   - the API (`apps/api`), as an `onRequest` hook before any route reads a session: the same rule where every write lands, so a path a front forgot is still closed;
   - open doors are only: the refusal page and its assets, the legal pages (terms, privacy notice, sanctions section), health probes, provider webhooks (payments, mail events), and unsubscribe links the law requires to keep working.
   The refusal page says plainly and kindly what the law is, that it is not about the person, that nothing in an account is deleted, and whom to write to if the place is wrong; it credits the geolocation dataset where its licence asks (decision 7). It never names the person.

7. **Geolocation is a port with local adapters.** `ranges_file` (default): a reduced range table (IPv4 and IPv6 ranges of the restricted places only, region level for Ukraine) generated by a script from a city-level dataset the operator obtains; the recommended source is DB-IP "IP to City Lite" (CC BY 4.0, no account or key; attribution on the refusal page and in the privacy notice); the table names its dataset and month. `edge_header`: a country and region header written by a CDN or edge the operator trusts, read only from the configured trusted proxies (the same trust rules as `API_TRUSTED_PROXIES`). `upstream_gate`: an upstream place check already refuses restricted places before traffic reaches the hub (the hosted preview's private network); it must be attested in the setup wizard. `fake`: deterministic answers for documentation address ranges (RFC 5737, RFC 3849), refused in production. The client address is read only through the trusted-proxy rules, is used for the lookup and is never written to a log line, a record or an outbox payload: a record names the place and the dataset. A table older than two months raises an operations warning; the monthly refresh is a worker schedule (SANC-002). There is no silent "off": in production the API refuses to start without an explicit gate mode (the configuration guard of OPS-001), and a web process without one logs a warning, reports the gate as unconfigured and keeps the launch gate `sanctions_screening_configured` open (its evidence includes the gate mode), while every write and every session still passes the API's gate.

8. **A sighting holds the person.** When a refused request carries a valid session (or an MCP or connection token), the person is **held**: a `jurisdiction_hold` row with the place, the source (`geolocation`, `edge_header`, `self_declared`, `payout_country`, `staff_report`), the dataset and the time. An open hold refuses the person on every request from anywhere (principal resolution treats them as signed out and the API answers `auth.jurisdiction_hold`) and at sign-in by name, with kind words; their agent, their MCP connections and their mandates stop acting; a company representative whose accountable person is held suspends (ADR 010 decision 9). At most one open hold per person; a second sighting keeps the first. A missing or invalid session holds nobody; a front never accepts a client-supplied identity or address as a sighting. A hold is cleared only by a compliance reviewer who has established that the person is not in a restricted place, with a reason and the evidence category, never by the person themselves; the person is told; the cleared row stays on record and a new sighting holds again.

9. **Self-declared places count.** A restricted place is refused wherever a person or company enters one (already true in the kernel). When the declaration is about the person's or company's own location (residence, profile location, company organisation or operating places in the ownership declaration, payout country), it is also a sighting: the person (or the company's declaring representative) is held with source `self_declared`. A place entered for something else (a supplier's location on an RFQ, a project site) is refused but holds nobody.

### List screening

10. **Lists are data, ingested by the worker.** Every hub screens against the **baseline**: OFAC's Sanctions List Service exports, the SDN list and the consolidated non-SDN lists, primary names and aliases. They need no key, and the engine's author and the reference operator are US persons. The baseline cannot be disabled (this keeps [Hub administration](../engine/hub-administration.md) guard rail 6 and replaces its "Consolidated Screening List" wording, which needs a key). The trade.gov Consolidated Screening List (adding the Commerce and State lists) is an additional list when the operator provides a key (the INTL-SAN adapter, which keeps refusing to run without one). A hub adds national and international lists (for example the UN Security Council consolidated list, the EU consolidated list, the UK sanctions list, national lists) through country-pack `sanctions` facts that name an adapter. Each list version is immutable: source, publication date, fetched time, entry count, the digest of the normalized entries. Ingestion modes are `file` (the operator drops an official export into the data directory; no network), `live` (downloaded through the egress proxy after provider activation by a second person, KEYS-001) and `fake` (synthetic entries for tests). A version is activated only after it parses and passes sanity bounds (an entry count that drops by more than a configured share needs a person's confirmation), so a truncated download never "clears" anyone. Freshness: each list has an expected cadence; past the warning age the console shows it; past the maximum age the list counts as **stale**, and a stale baseline makes every money and commitment gate refuse (decision 13).

11. **Matching is deterministic first, fuzzy by configuration.** Names are normalized into keys: lower case, compatibility decomposition with marks removed, punctuation dropped, transliteration into Latin by published tables (ICAO Doc 9303 for Cyrillic; Georgian, Armenian, Arabic and other scripts added as data tables with their sources), distinct tokens sorted. Persons are compared with individual entries, companies with entity entries (vessels and aircraft only when a hub enables them). The engine rule (parity with Contribuda): a possible match when the subject's tokens are all among an entry key's tokens with at most one more on the entry's side, or the entry key equals the subject's tokens minus one (for subjects of three or more tokens). A one-token name is never reported as clear: the outcome is `insufficient_name`, which a reviewer resolves with more data. A hub may add a **fuzzy** layer (token similarity with a threshold within engine bounds, for example Jaro-Winkler at or above 0.90 per token) that can only **add** possible matches; no setting can make matching looser than the engine rule's recall or let any score auto-clear. Secondary attributes (dates of birth, nationality, addresses, identifiers in the entry) are shown to the reviewer and never used to clear automatically.

12. **When screening runs.** Persons: at registration (verified e-mail), at every sign-in when the newest active list versions are newer than their last screening or their names changed, on every change of name or legal name, and when they become a payee. Companies: at creation, on change of name, registration identifiers, officers or the ownership declaration, at claim and verification (HUB-003 recipes call the engine as the `sanctions_screening` check), and when they become a seller above the hub threshold or a payee. Counterparties: before the first commercial commitment between two parties and before every quote sent, order accepted or agreement signed, a fresh screening result is required for both sides. Payees: before a payout account is created and before every payout. Event organizers taking payments, financing partners and federation peers' operator entities: at onboarding and on change. The hub operator: in the setup wizard. Everyone active: again on every new list version (delta re-screening, SANC-005) and on a weekly safety-net schedule. Screening runs in the worker from outbox events where it can, synchronously where a gate needs the answer now; a failure is retried and logged, never turned into "clear".

13. **Outcomes are honest and gates fail closed.** A screening result is one of `clear` (screened against named active list versions, no possible match), `possible_match`, `insufficient_name` or `not_screened` (no active version, stale baseline, adapter error). Only `clear`, or a decided `not_same_person`, against fresh list versions lets money move or a commitment bind. Sign-in itself is not refused for an open possible match (a name alone is mostly a false positive; parity with Contribuda), but while one is open, or a match is confirmed, or the state is unknown, the subject's money (payout accounts, payouts, ticket and course sales, consultation fees) and commercial commitments (quotes, orders, agreements) stop, and their agent cannot commit. A gate that cannot get an answer refuses: no money moves unscreened.

### Review, decisions and what people are told

14. **Review cases with separation of duties.** Each subject with open possible matches is one queue item for compliance staff, late after one business day (hub setting); notifying compliance staff cannot be muted, and the notification names nobody. Decisions: **confirmed** by one compliance reviewer (the safe direction): the subject is suspended (account or company), their agent stopped, open money and commitments frozen in the providers' hands (Trustwork never holds funds, ADR 010 decision 20), and a report draft prepared for the operator's blocked-property or rejected-transaction reporting (US: 31 CFR 501.603 and 501.604, ten business days; filing stays the operator's). **Not the same person** needs two people: the reviewer and a second person with a compliance permission, neither the subject, neither with a declared conflict; the reason and evidence category are recorded. A decided entry is not flagged again for the same subject unless the entry's normalized names change. An **appeal** by the subject is decided by a reviewer other than the one who decided; reversing a confirmation needs two people. Reviewers see the entry and the screened names under the case; they never see private data the case does not grant (ADR 002, DATA-002 case grants).

15. **The subject is told only what the law allows.** A held person sees the refusal words; a person with an open possible match sees that a compliance check needs a person's review and that payments and payouts are paused, with the contact, never the list or the entry; a confirmed subject is told their account is suspended for legal reasons with the contact and appeal path, as far as the hub's law allows (tipping-off rules are country-pack facts). A counterparty sees only that the other side cannot transact now, never why.

### Records, privacy and operations

16. **Guard rails no console can switch off.** The restricted list cannot shrink; the baseline lists cannot be disabled; matching can only be tightened; money and commitment gates cannot be turned off; holds and confirmed matches cannot be cleared by the subject or without a reason; nothing of this module ever changes ranking, matching, recommendations or reputation (a screening outcome is never a reputation signal and never public).

17. **Records and erasure.** Holds, screening results, matches, decisions and refusal counts are append-only (decisions are new rows or guarded single transitions) and kept for the hub's sanctions record-keeping period from the country pack (US: ten years, 31 CFR 501.601); a person's erasure keeps them, pseudonymized where the law allows, naming the erasure tombstone (PRV-001). No network address is ever stored. Refusals are counted per day and place for metrics; no per-person refusal log exists beyond the hold.

18. **Metrics without surveillance.** Hub cohorts only: refusals per place and day, open holds, holds cleared and median time to clear, possible matches opened, decided, late, the not-same-person share (the false-positive rate), list and geolocation dataset ages, re-screening duration, gate refusals by kind. No per-person behaviour view.

### Ownership and licensing

19. **Where the code lives.** Contracts in `packages/contracts/src/sanctions.ts`, together with the pure primitives both the web and the API need at run time (restricted-place resolution from the injected authoritative list, address parsing, the range table and the geolocation adapters), because the web and both backend images ship the contracts package. Operator tooling (the range-table generator), name normalization, matching and list parsers go to `packages/compliance`; the slice that first needs them in the worker or the API at run time (SANC-002) adds `packages/compliance` to the backend images with the maintainers' agreement, or keeps them in the contracts package. Storage and use cases per slice: `jurisdiction` (SANC-001), `screening-lists` (SANC-002), `screening` (SANC-003), `screening-gates` (SANC-004), `rescreen` (SANC-005), attestation (SANC-009). HUB-003 keeps verification adapters and recipes and calls the screening engine for its `sanctions_screening` check instead of owning sanctions lists; its title and acceptance change accordingly. PAY-001, BILL-002, EVT-001, FED-001, HUB-004 and HUBC-009 depend on the slices they must call.

20. **Reimplemented, not copied.** Trustwork is AGPL-3.0-only and public. The design reproduces Contribuda's behaviour from its ADR and code; no Contribuda source file, generated range table or generated list file is copied. The OFAC exports are works of the US government; the geolocation dataset is the operator's to obtain under its own licence, with the attribution the licence requires.

## Alternatives

- **An engine kill switch that geolocates the server**: rejected by the owner (decision 3).
- **Only the hosting landing's place check** (today's preview): kept as the `upstream_gate` mode, but not enough for an engine whose reference hub will be public and whose other operators have no such landing.
- **A commercial screening provider as the baseline**: needs accounts, keys and spending; the baseline must work keyless. Providers remain possible as additional list adapters.
- **Lists generated into code** (Contribuda): simple, but every list refresh would be a release of the engine for every operator; database list versions refreshed by the worker keep operators independent and make re-screening automatic.
- **A single administrator clears matches** (Contribuda): Trustwork's hub administration already requires two people for sensitive actions; a false clear is the dangerous error, so it gets the second person.
- **Refusing sign-in on a possible match**: rejected for parity and proportionality; money and commitments stop instead.
- **Probabilistic matching with auto-clear below a score**: rejected; no score ever clears.

## Consequences

- New migrations in module directories `jurisdiction`, `screening-lists`, `screening` and `attestation`; new namespaces `jurisdiction` and `screening` in every locale.
- The production API configuration needs an explicit jurisdiction-gate mode (the hosted preview sets `upstream_gate`); the deployment notes of SANC-001 say so, and the conductor sets it before the next preview deployment of the API.
- HUB-003 no longer owns sanctions lists; PAY-001, BILL-002, EVT-001, FED-001, HUB-004 and HUBC-009 gain dependencies and acceptance lines.
- A person travelling in a restricted place is refused there and held; back home they write to the hub and a reviewer clears the hold. A geolocation error refuses someone who is not in a restricted place; the page tells them how to reach the hub.

## Open questions (owner and counsel)

1. Lists for the US reference hub beyond the OFAC baseline: add the Consolidated Screening List (needs a trade.gov key, BIS Entity List and others), or the BIS lists separately? Should non-US hubs keep the US baseline (current rule: yes, it cannot be disabled)?
2. Geolocation for the reference hub once it leaves the private network: DB-IP Lite ranges file (no account; CC BY 4.0 attribution), a CDN country header (needs a CDN in front of the hub), or both?
3. Matching thresholds: keep Contribuda's exact-key rule only, or enable the fuzzy layer for the reference hub (which threshold)?
4. Review service level (one business day) and who holds the compliance-officer role for the reference hub; is a single reviewer acceptable for clearing holds?
5. Record-keeping period and pseudonymization of retained screening records after erasure in each launch country; tipping-off rules for what a subject may be told.
6. Counsel: the wording of the brand policy for forks in restricted places, the export-control wording for publishing the source, the refusal-page text, Terms section and privacy section.
7. Whether the weekly safety-net re-screen is enough for the reference hub, or daily.
