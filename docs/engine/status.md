# What works today, and what is designed

We would rather under-promise. The normative requirements of every module, with a status per requirement, are in the [module specifications](modules/README.md). This page says, area by area, what you can run today, what exists only as a demo on synthetic data, what is frozen as a contract, what is designed, and what this handbook proposes for the first time. It is updated whenever a work package is accepted.

## Status levels

| Level | Meaning |
|---|---|
| **Live** | Implemented end to end on PostgreSQL with automated tests, including negative authorization tests. Not yet deployed to production anywhere. |
| **Demo** | The user interface exists and is tested in a browser, but it runs on synthetic demo data (`apps/web/fixtures`). Nothing is stored; buttons that would act externally are imitations and say so. |
| **Contract** | The data shapes, state machines and invariants are frozen as Zod schemas in `packages/contracts` with tests. No storage or API yet. |
| **Designed** | An accepted design document or ADR describes it; no code yet. |
| **Proposed** | Designed in this handbook for the first time (owner decisions of 2026-10-30 and 2026-10-31). Open for review and discussion. Each proposed area has work packages in the [roadmap](roadmap.md). |

## What this means if you try it

- `TRUSTWORK_DEMO_MODE=1 npm run dev:web` shows the whole public site and workspace on synthetic data set in Uzbekistan, in seven languages; a synthetic United States demo hub replaces it in the platform phase (DEMO-US). Personas are chosen with `?persona=reader|mixed|owner`, only in demo mode.
- `npm run dev:api` with the local database and the restricted runtime role printed by `npm run seed:dev -w @trustwork/api` runs the live identity, company and project API under `/v1/*` ([agent onboarding](agent-onboarding.md#3-install-and-run) has the exact commands).
- The API process has a production runtime baseline (OPS-001): it refuses to start with `NODE_ENV=production` without `AUTH_FLOW_SECRET`, an `https` `PUBLIC_ORIGIN` and secure cookies; writes one redacted JSON log line per request; answers `GET /health/live` and `GET /health/ready` (database and migration ledger); exports OpenTelemetry-compatible traces and metrics only when `OTEL_EXPORTER_OTLP_ENDPOINT` is set; and sends security headers. Web pages carry a per-request nonce-based Content Security Policy. Nothing is deployed to production.
- `docker compose -f infra/compose.yaml --profile stack up --build -d` runs the whole platform from its container images (OPS-002): PostgreSQL, a one-shot migrate job under the migrator role, the API, the worker, the web app, S3-compatible storage and a proxy that serves one origin with `/v1/*` routed to the API; sign-up and login work through it locally and in CI. The images are non-root and carry no development dependencies; nothing is deployed ([container images](../operations/images.md)).
- Backups and restore are scripted and drilled on synthetic data (OPS-003): encrypted base backups with WAL archiving, logical dumps and file copies to an off-host target through an adapter, point-in-time restore into an isolated project with runtime logins fenced until tombstone replay and reconciliation against provider receipts are done, and audit/outbox partition retention within the hub policy. CI runs the drill; no production backup target or schedule exists ([backup and restore](../operations/backup-and-restore.md)).
- With demo mode off (the default, WEB-004) the web app runs on the live API through the same-origin `/v1/*` route: sign-up, e-mail verification, sign-in and sign-out, recovery, step-up, sessions and password change, company creation and inviting colleagues (the invitation landing page follows the MAIL-001 links), and creating and publishing projects work in the browser, and the public company, people and project pages show only what the API serves. Modules without an API yet (editorial, events, magazine, academy, procurement, sales, assistant) show their empty states; no fixture and no `?persona=` reaches a page. A browser suite runs these flows against a real API and database (`tests/web/live-api`).
- No payment, e-mail, model or registry provider is connected. Mail goes through the outbox and the worker with a provider-neutral SMTP adapter, but no deployment points it at a mail server yet (the default transport is the recording fake); Google and Apple sign-in have a fake mode and a live mode that needs keys nobody has configured; the sanctions screening adapter needs a key; payment, model, registry, storage and channel providers are designed ports with fakes.
- The worker (REL-001) relays the outbox and runs durable jobs and scheduled maintenance under its own database role. Domain handlers: mail delivery (MAIL-001), files (FILE-001, with storage configured) and agent action dispatch and reconciliation (AST-001, only with `ASSISTANT_EFFECTS=fake`, because only fake providers exist); other outbox events are marked published as unhandled until their consumers exist.

## What has not been validated

- No interviews with practitioners have taken place yet (open research O01).
- No real company, person, review or rating exists in the engine.
- Translations into Uzbek, Georgian, Armenian and Azerbaijani are machine drafts produced by the integrator and await review by native speakers.
- Country facts that cite only secondary sources are marked as pending official confirmation inside each pack.
