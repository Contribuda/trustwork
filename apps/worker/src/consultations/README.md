# Consultation context reminders (CONS-001 / COMMS-001)

Status: implemented locally, in review; fake channel and mail adapters tested. No real provider delivery, operational template activation or deployment is claimed.

The existing authenticated booking confirmation opens/finds the agreement thread under its participant principal and RLS. The worker never sets that principal and cannot open a thread. Public `ThreadSchema`, message-author variants and template/event vocabularies are unchanged.

Confirmation captures the trusted API serving context (`TRUSTWORK_HUB_ID`) in the immutable, internal `consultation_reminder.source_hub_id`. This is the hub that actually accepted confirmation, not a locale, company address or the later worker's default. No public command or contract field is added. One API process serves its configured hub; multiple such hub processes may share the node database. Unconfigured confirmations and legacy rows retain NULL provenance, remain unavailable for dispatch and are never guessed or backfilled.

With the matching `TRUSTWORK_HUB_ID` configured, the registered `consultation.reminders.<hub UUID without hyphens>` task polls at most 100 due scheduled rows for that stored hub every 60 seconds. The existing day/hour cadence and `(booking_id, offset_minutes)` identity are preserved. Each row commits its system message, agreement link, identifiers-only audit/outbox, recipient notifications, internal receipt, mail intents/channel jobs and `sent` transition in one transaction. The message ID is unique on the reminder. A crash before commit leaves no partial effect; duplicate ticks or workers serialize on the booking and reminder. No catch-up after the slot starts is added; unavailable/expired reminders retain their scheduled record for inspection.

The producer and final dispatcher independently check the stored source hub. Mail jobs (`consultation.mail.<hub UUID>`) and channel jobs (`consultation.notify.<hub UUID>`) are routed from that provenance; a worker registers only its hub's job kinds. The generic relay can enqueue either hub's job without sending it. Another hub cannot consume the attempts or apply its brand. Scheduler row names also include the source hub, so one hub cannot take another hub's polling interval. Legacy unscoped channel jobs remain unavailable; existing unknown outcomes still require reconciliation, never automatic migration/replay.

Copy comes from the source hub's existing `thread.message` template, activated by a second person in all seven engine languages. No template is installed or activated automatically. The system message uses the hub default language; external notifications choose the recipient's language under existing locale fallback rules. Parameters contain only the agreement kind and empty author/subject strings: no question, site address, client ceiling, licence number or message body enters notification parameters. The governed copy should be a minimal context activity/reminder prompt. The seven-language synthetic test fixture is not an operational template or native-language review.

`messages` notification preferences, verified mail addresses, suppression and channel grants apply unchanged. Daily/weekly digests are not immediately sent. Existing channel kinds only: email through MAIL-001 and messenger/SMS through a recording fake. The fake uses delivery ID as its stable identity and deduplicates within its process. Durable job state prevents automatic replay across a restart; an explicit retry requires evidence of no external effect. This module registers no real messenger provider, reply ingestion or new channel.

Before the context effect and again at final dispatch, SQL checks the booked state, the open agreement thread, current recipients/company deal permissions, the pinned licence, suspension and jurisdiction holds. A reminder is not a new money commitment: a pending money-only screening review does not by itself block communication. Applicable sanctions checks hold the existing screening locks. Booking, membership, licence and grant locks order revocations against the final effect; the mail check also validates the current primary verified address. Preference writes (INSERT, UPDATE and DELETE) take an exclusive transaction advisory lock on person/category/channel; the final dispatcher holds its shared counterpart, including when no preference row exists. A separate statement after acquiring the lock reads the committed preference. Suppression writes and final mail dispatch likewise serialize by address hash, including the first unsubscribe. Readers intentionally do not row-lock preferences, avoiding an update-row/advisory-lock inversion.

Provider dispatch holds these locks through the bounded adapter call and records its receipt in the same transaction. Already committed external effects cannot be recalled.

Local `consultation_reminder.status = sent` means only that the system message reached the context transaction. Its receipt provider is `internal`. Mail enqueue remains pending; a fake/provider acknowledgement is not evidence of recipient delivery. External jobs preserve unknown outcomes, stable identities and REL-001 fencing. An exception/crash/ambiguous adapter outcome parks the job; never retry without reconciliation. Use the existing worker reconciliation workflow with actual evidence. A succeeded/failed reconciliation settles channel state on the next reminder tick; a confirmed-no-effect queued reconciliation rechecks access before attempting again. Duplicate final jobs do not resend.

Separate-process tests use actual preference API calls and database barriers for both race orders on email and messenger, and two independently configured hubs with different governed copy. Only recording fakes run.
