# Consultation context reminders (CONS-001 / COMMS-001)

Status: implemented locally, in review; fake channel and mail adapters tested. No real provider delivery, operational template activation or deployment is claimed.

The existing authenticated booking confirmation opens/finds the agreement thread under its participant principal and RLS. The worker never sets that principal and cannot open a thread. Public `ThreadSchema`, message-author variants and template/event vocabularies are unchanged.

With `TRUSTWORK_HUB_ID` configured, the registered `consultation.reminders` task polls at most 100 due scheduled rows every 60 seconds. The existing day/hour cadence and `(booking_id, offset_minutes)` identity are preserved. Each row commits its system message, agreement link, identifiers-only audit/outbox, recipient notifications, internal receipt, mail intents/channel jobs and `sent` transition in one transaction. The message ID is unique on the reminder. A crash before commit leaves no partial effect; duplicate ticks or workers serialize on the booking and reminder. No catch-up after the slot starts is added; unavailable/expired reminders retain their scheduled record for inspection.

Copy comes from the hub's existing `thread.message` template, activated by a second person in all seven engine languages. No template is installed or activated automatically. The system message uses the hub default language; external notifications choose the recipient's language under existing locale fallback rules. Parameters contain only the agreement kind and empty author/subject strings: no question, site address, client ceiling, licence number or message body enters notification parameters. The governed copy should be a minimal context activity/reminder prompt. The seven-language synthetic test fixture is not an operational template or native-language review.

`messages` notification preferences, verified mail addresses, suppression and channel grants apply unchanged. Daily/weekly digests are not immediately sent. Existing channel kinds only: email through MAIL-001 and messenger/SMS through a recording fake. The fake uses delivery ID as its stable identity and deduplicates within its process. Durable job state prevents automatic replay across a restart; an explicit retry requires evidence of no external effect. This module registers no real messenger provider, reply ingestion or new channel.

Before the context effect and again at final dispatch, SQL checks the booked state, the open agreement thread, current recipients/company deal permissions, the pinned licence, suspension and jurisdiction holds. A reminder is not a new money commitment: a pending money-only screening review does not by itself block communication. Applicable sanctions checks hold the existing screening locks. Booking, membership, licence and grant locks order revocations against the final effect; the mail check also validates the current primary verified address. Provider dispatch holds these locks through the bounded adapter call and records its receipt in the same transaction. Already committed external effects cannot be recalled.

Local `consultation_reminder.status = sent` means only that the system message reached the context transaction. Its receipt provider is `internal`. Mail enqueue remains pending; a fake/provider acknowledgement is not evidence of recipient delivery. External jobs preserve unknown outcomes, stable identities and REL-001 fencing. An exception/crash/ambiguous adapter outcome parks the job; never retry without reconciliation. Use the existing worker reconciliation workflow with actual evidence. A succeeded/failed reconciliation settles channel state on the next reminder tick; a confirmed-no-effect queued reconciliation rechecks access before attempting again. Duplicate final jobs do not resend.

Verification: `tests/consultations/reminders.test.ts`, the consultation API/contracts, COMMS-001 tests, MAIL-001 tests, access/migration inventories and the BE-005 per-module crash case. No full local build/gate is run under the conductor's load rule. PR #392 records exact-commit results and outstanding full CI separately.
