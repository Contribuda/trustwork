# Federation node (FED-001)

Node identity, the Ed25519 key chain, the signed manifest, RFC 9421 request and response signatures, the handshake and peering records of the mesh protocol `trustwork-mesh/1` (`docs/engine/federation-protocol.md` sections 4 to 8; ADR 011 decisions 2, 6 and 12). Contracts: `packages/contracts/src/federation.ts`. Data: `packages/data/migrations/federation-node`, `packages/data/src/schema/federation-node.ts`, `packages/data/src/repositories/federation-node.ts`. Tests: `tests/federation/node`.

## Files

| File | Holds |
|---|---|
| `crypto.ts` | The only code that touches a private seed: key generation, the `NodeSeed` that never serializes, the `NodeKeySealer` (AES-256-GCM data key wrapped by the KEYS-001 key-encryption key, own additional authenticated data per node and key), the Ed25519 verifier port |
| `http-signatures.ts` | Signing of the node's own requests and responses, verification of received messages: body digest, coverage, window and clock skew, nonce (replay), key selection against the sender's chain, signature |
| `federation-node.service.ts` | Use cases: manifest assembly and publication, peer manifest validation and SANC-008 admission on declared, attested and observed evidence, handshake in both directions, double opt-in records, suspension, defederation, refresh (daily, after `federation.key_unknown`, on demand), revocation re-verification, equivocation, flow gates for later packages |
| `federation-node.controller.ts` | `GET /.well-known/trustwork/manifest.json`, `POST /federation/v1/handshake` (no session, signature-authenticated, signed answers) and the console routes under `/v1/admin/federation` |

## Rules kept here

- The private seed exists only in the memory of the process that signs; the database holds the sealed seed (ciphertext under the KEK, which never enters the database) in a table no runtime role can read, reachable only through `federation_node_signing_material`, which answers only inside a transaction the signer path marked (`trustwork.federation_signer`); no endpoint, log line or audit row carries a seed or a signature secret.
- **The trust anchor for a peer's keys is its own manifest fetched from `https://<peer>/.well-known/trustwork/manifest.json`, never a request body.** A handshake is verified against the chain we hold (refreshed from the origin when the key label is unknown, fetched on first contact), and the manifest it carries must equal the one the origin serves. For a known peer a fetched manifest must chain from the held keys (same genesis, every held key unchanged, retirements and revocations kept), must not be older than the held one and must never drop a published revocation; a changed genesis or key is recorded for staff (`equivocation_at`), closes every flow and keeps the held manifest; a rollback or a dropped revocation is refused and the held manifest kept. There is no command yet to clear an equivocation finding (the operator confirms the chain out of band; NET-003's operator channel).
- **Nothing unauthenticated writes peer state or a record naming a peer.** An unsigned, malformed, stale or forged request is answered with the protocol code and counted, nothing more: no refusal record, no suspension, no refresh moved. The shape checks (digest, coverage, window, skew, nonce present) run before any key work, so a request with an unknown key label cannot make this node fetch unless it is otherwise well formed, and an inbound request makes this node fetch a host's manifest at most once per host per 10 minutes (`INBOUND_FETCH_COOLDOWN_MS`). A first contact from an unknown host fetches without writing anything durable until the signature verifies against what was fetched. The nonce is remembered only after the signature verified, so a forgery cannot poison a peer's nonces.
- **Only a fetch from the peer's origin moves `refresh_due_at`.** A verified handshake or a deal re-admits the peer but keeps the refresh due (`federation_peer_record(..., p_fetched := false)`), and a handshake that finds the held manifest due fetches first, so a stolen key cannot keep an archived manifest alive past the next due refresh: the published revocation is seen and the key refused.
- **Outbound connections fail closed.** The peer's name is resolved first; a private, loopback, link-local or otherwise non-public address is refused; the address is judged by the jurisdiction gate, and only a gate that judges addresses (`ranges_file`, or `fake` in tests) can clear it: with `edge_header`, `upstream_gate` or no gate the node connects nowhere and says that address judgement must be configured before federation goes live (no provider, account or external call is added). A restricted address is refused with a refusal record naming the place, never the address, and pauses every flow with a held peer. The connection then goes to exactly the judged address with the TLS checks on the name, under an absolute deadline per exchange (20 s) on top of the idle timeout, so a dripping peer stalls no refresh run and no shutdown. Bodies over 256 KiB are refused before they are read (requests) or dropped (peer answers).
- A refusal names only the host the manifest was fetched from; a manifest whose `node` differs from that host is refused as invalid without naming the node it claims.
- Every peering record, refusal record, event and manifest is checked for network addresses at the database; nodes are DNS names.
- Only launched hubs (`soft_launch`, `public`, `suspended`, `closing`) appear in the manifest or can be addressed by a handshake or a request; a `draft` or `preparing` hub is refused like an unknown hub, so the public URL reveals nothing about it (owner default under ADR 025, 2026-11-04).
- A record becomes `active` only with both acceptances and the admission reference, and above `trust_verifications` only with a consumed second-person approval (`federation.raise_peering_level`) of exactly that hub pair and level. Key rotation is the second-person action `ops.rotate_node_key`.
- Defederation ends the record and never rewrites history; suspension pauses flows without changing the protocol state. The admission check runs again on every manifest or attestation change, before the first delivery of every new deal, and at least daily; a refusal or an expired attestation suspends every flow with the peer, a renewed admission lifts what it caused.

## The daily refresh

`FederationRefreshTimer` runs `FederationNodeService.refreshDueLocked()` every 6 hours from the API process whenever the node reaches peers (the HTTPS transport: production or `TRUSTWORK_FEDERATION_TRANSPORT=https`; offline stays off, no extra flag). One instance refreshes at a time under the PostgreSQL advisory lock `trustwork.federation_refresh`; the timer is cleared on shutdown; a peer that fails is logged and left due. Independently of any timer, `federation_peer_current` makes a peer past its refresh by more than a day, or with an expired attestation, count as not admitted at every point of use (flows, handshakes, requests, acceptances, lifting a suspension) until a fresh admission. The proper home of the refresh is the worker; that move needs worker grants on the `federation_*` functions, the admission code shared outside the API module and the transport, KEK and geolocation configuration in the worker process.

## Ports for later packages

`FederationNodeService.verifyPeerMessage` (FED-002, FED-004: verify a peer's signed request, refreshing its manifest once on an unknown key), `flowAllowed` (the level a feed pull, badge or delivery needs), `admitDealDelivery` (the re-run before a deal's first delivery), `refreshDue` (the worker's daily refresh) and the `ReverificationPort` the replica and deal stores register for published revocations.
