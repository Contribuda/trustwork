# Payments (PAY-001, partial)

The HTTP service creates immutable payment instructions; provider effects run through `apps/worker/src/payments`. The default registry has no provider. No operational source binding or rail is seeded. This is not PAY-001 acceptance.

## Boundaries

- `POST /v1/payments` accepts only `agreementId` and the original order's `budgetId`. Creation checks current buyer/session/company authority, accepted agreement and quote terms, the owning source, SANC-004 and current collecting-hub/provider configuration. It reuses the order's BILL-001 transaction reservation, including its existing amount/currency and authority. No second reserve is created.
- `GET /v1/payments/:id` returns the original requester's limited summary, with current membership required for a company. It never returns private agreement halves, screening details, the connected account or provider configuration. Synthetic success is explicitly `synthetic_no_money_moves`.
- `POST /v1/payments/:id/{confirm,refund,payout,connected-account}` accepts an empty body. Each follow-up has one stable operation ID. Refund/payout use the exact original success and account; full refund and payout cannot overlap. Account verification refers to a prebound account, not caller-supplied account registration.
- Every mutation completes BE-005 in its transaction. The outbox contains only the operation ID. Restricted API/worker roles have no raw payment-table grants.

## Dispatch, evidence and recovery

A real leased job/fence/attempt marks the operation `outcome_unknown` before the provider boundary. A second transaction locks current authority through dispatch and checks elapsed session/lease expiry after all waits. A crash between transactions retains the hold and permits only lookup of the original operation. No timeout or missing lookup result proves non-payment.

The optional worker ingress (`PAYMENTS_WEBHOOK_PORT`, loopback only; deployment owns TLS/routing) accepts at most 8 KiB of raw bytes. Provider authentication precedes parsing or database receipt acceptance. The shipped empty registry rejects all senders. Immutable receipts distinguish identical delivery, reordered notices and conflicting semantic outcomes. A terminal receipt can close the original reservation after dispatch authority is revoked. Recorded provider acknowledgement also reconciles a REL job parked after receipt commit but before worker acknowledgement. A pending customer-action acknowledgement completes only dispatch: the payment stays pending, its hold remains and lookup continues.

`payments.lookup_due` schedules bounded original-operation lookups. A phone/QR deadline never releases the BILL hold or creates a new charge. No currency conversion, reference rate, operator-held balance or ranking/reputation dependency exists.

## Registered local source authority

The agreement/person/company stores still have no home-country or account authority. Residence and account facts are never inferred from locale, IP, current membership, reminder source hub, deployment country or an untrusted request. Proposed [ADR024](../../../../../docs/adr/024-payment-source-authority.md) received a bounded conductor allocation for the individual, same-hub commercial-order slice; implementation review remains pending.

The source path is implemented separately from existing agreement acceptance:

1. An installation-only command proposes a versioned identity-link, account or fixed publisher registration. A distinct currently elevated human approves its exact digest; activation rechecks both permissions, scope, session and expiry. Raw app/worker roles cannot register themselves. There are no seeded registrations, operational adapters or verifier credentials. The fixed synthetic publisher implementation identifier is the SHA-256 digest of `synthetic-publisher-v1`; arbitrary publisher implementations cannot activate this projection.
2. `POST /v1/payments/sources/challenges` uses the exact current person/session/epoch, a server nonce, purpose, issuer and connection. It accepts no substitute party. A registered adapter authenticates an Ed25519 envelope at `/payments/sources/:registrationId`; a separate narrow verifier identity stores only challenge-bound assertions. The account assertion must match an independent identity issuer's subject AND provider entity, connection digest and country/subdivision. The bounded initial slice requires both payments and payouts capabilities. `verified=true`, names, email matching and account control alone cannot establish identity. The shipped adapter is explicitly synthetic; its facts establish no real identity, account or funds.
3. `GET /v1/payments/sources/bindings` returns only the person's opaque binding IDs. A scoped staff proposer obtains technical digest material at `/v1/admin/payments/source-bindings/:id/review`; `/activate` consumes an exact independent ADM approval. The reviewer differs from the participant, proposer and accountable issuer. The authorization also excludes either original contracting person from either review. No staff endpoint returns identity subjects, account/entity references, signatures or country evidence without a case grant.
4. `POST /v1/payments/sources/authorizations` reads the original accepted commercial agreement, quote, RFQ and order/reservation, exact versioned sources and current screening. It constructs a complete immutable authorization digest. Both original individuals separately accept that digest at `/authorizations/:id/accept`. Only the second acceptance publishes `payment_source_version` and its current reference. A historical agreement supplies neither receipt. Source changes need a new bilateral version; any existing payment intent prevents replacement, including an unknown original effect. No additional BILL reservation is created.
5. First-party `/v1/payments/sources/:id/revoke`, scoped staff `/v1/admin/payments/source-bindings/:id/revoke` and a signed issuer withdrawal narrow their exact records. Issuer withdrawal binds the issuer's original assertion ID and digest; it cannot replace facts. Immutable history remains. A source/referral/receipt/key timeout or revocation prevents fresh effects but never releases an unknown financial hold. Late original financial receipts remain consumable.

All source rows are FORCE RLS with no raw API/worker privileges. The operational source registry remains empty; source runtime wiring is installation-owned, never a callback option. The internal verifier grants are only `payments_source_verifier_registration(uuid)` and `payments_source_record_assertion(jsonb)`. The fixed publisher has no runtime execution grant. Intake is limited to 8 KiB, challenges to ten minutes, assertions/authorizations to at most 24 hours, and SQL waits to five seconds. Source evidence and financial receipts are distinct trust boundaries.

The current reference, all source revocation records, original party sessions/epochs, agreement and current route/screening stay locked through dispatch. An already-held source writer fails closed with a domain refusal; a later revoker waits for the bounded payment effect. Source expiry is checked again after domain waits. Country-only evidence cannot clear an unknown subdivision: signed subdivision facts must pass owning HUB territory/jurisdiction and SANC checks for both parties. A shared responsible hub is routing, not proof of domicile or legal eligibility.

The historical owner-created `payment_source` fixture is limited to `synthetic` evidence. It is not an operational publisher or a company-source implementation. New positive source tests do not insert that projection. Companies, delegated actors, tasks, consultations and two-sided remote screening remain unavailable in the registered path. A valid historical synthetic local binding with no configured route records `outside_platform`. Licensed providers, operational rails and legal/operator policies remain UNKNOWN. No SDK, network provider call or account provisioning is included.

Initial dispatch and receipts lock intent, operation, then BILL resources. Worker admission statements are bounded to five seconds; the actual job abort also stops awaiting an uncooperative adapter and releases authority locks. A late effect remains unknown until its original operation is reconciled.

## Current authority and trusted receipts

Each new operation captures the exact admitting person epoch and, for a company payer, company epoch and membership ID. Membership locks precede person/company locks to match the owning membership revoker. The worker checks those immutable admission facts against current authority after all domain waits; an old queued operation without a captured snapshot is unavailable for fresh dispatch. New HTTP commands may resolve current authority, but cannot silently refresh an already queued operation. Wall-clock session, job lease, budget and screening freshness are checked at the final boundary. HTTP write and receipt waits are bounded too.

Raw `trustwork_app` and `trustwork_worker` identities cannot call `payments_receipt` or fabricate source/rail/account evidence. A separately provisioned trusted verifier login may receive schema USAGE and EXECUTE on `payments_receipt(jsonb)` only; it receives no app/worker membership or raw table privileges. `PaymentRuntime.receiptPool` belongs to the authenticated adapter ingress, not a request parameter. No verifier login, credential or operational provider is provisioned by this change. Without that pool, evidence ingestion refuses and unknown holds remain. Tests provision a synthetic verifier identity and authenticate fake-provider evidence before its command. Operational source attestors and verifier provisioning remain unavailable.

`tests/payments/authority.test.ts` uses real company agreements, HTTP commands, the registered worker and competing PostgreSQL transactions. Test-only barriers schedule owning revocation before the final SQL guard, after the durable marker, or while the provider boundary holds authority. They never substitute an authorization result. Both orders assert sends, no duplicate dispatch, retained unknown holds and late original evidence. Local evidence remains distinct from exact-head CI and maintainer acceptance.

`tests/payments/sources.test.ts` exercises the actual registered HTTP/issuer/approval/publication/worker path. Its source matrix covers every versioned revocation row, all five HTTP effects and final worker effects, in both writer orders. It verifies raw-role denial, exact source assertions, distinct review, bilateral receipts, unknown recovery, and expiry after waits. `tests/payments/source-crash.ts` plugs the seven source mutations into the existing BE-005 crash harness; historical payment cases retain their original meaning.

## Immutable HTTP request admission

Payment creation/actions and all seven source mutations opt out of `PrincipalService.runAs` stale-epoch refresh. If authority changes after authentication but before the mutation transaction, the original request returns 409 without entering its callback, changing its resolved principal, or committing a payment/source/outbox/success completion. The existing BE-005 interceptor may retain the 409 refusal envelope; this is not a successful business completion. A separately authenticated new request can use current authority. Unrelated callers retain default refresh, and PRV repeatable-read snapshot plumbing remains independent. `tests/payments/request-admission.test.ts` exercises every protected registered HTTP route and an owning membership epoch change, plus fresh positives and unchanged default/snapshot behavior.
