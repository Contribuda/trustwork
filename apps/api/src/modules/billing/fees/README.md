# Governed fees and public pricing (BILL-003)

Agent: Codex CLI (OpenAI) for Parshkov

Status: implementation in progress; not complete acceptance. No operational price is activated. All positive test rates and participants are synthetic. No provider, payment custody, account setup or deployment is introduced.

## Authority and immutable versions

`POST /v1/admin/billing/fees` drafts immutable terms for the server-configured hub. `POST /v1/admin/billing/fees/:id/activate` consumes a real scoped, elevated second-person approval for the exact canonical activation digest. The activator differs from the drafter and the approval's decision-maker differs from its requester. Database commands independently enforce live staff assignment, scope, elevation and audit; a request body cannot confer authority. Published intervals are immutable, half-open, cannot be backdated and cannot overlap general or matching category rates. Ordered advisory locks serialize concurrent activation and binding.

`GET /v1/pricing` is anonymous and returns only explicit public serializers. It lists current and future approved, nonexpired fee versions, active plan/price pairs, published service/module prices, model and capability sale versions, credit packs with their validity, and referral terms. It excludes private staff, approval, payer and provider-cost fields. Execution accounting is not a public sale price, and existing meter rates are not relabelled as a model or capability version. The page at `/pricing` and its six localized routes uses the same HTTP DataPort, all seven locales, the shared language picker, `Intl` and the brand module. Public consultation names resolve through the existing kind registry and locale keys; known task names resolve through the released work-type taxonomy and its seven label dictionaries. This display lookup does not authorize a commercial category mapping. Unknown category labels are explicitly unavailable; internal keys are never used as display labels. Exact version IDs and digests remain inspectable details.

Agent usage prices for modules, capabilities, catalogue models and meters are read from [agent metering](../agent-metering/README.md) into the same sections.

## Public catalogue coverage

Optional `coverage.generatedAt` is one owning API snapshot time. Each of `fees`, `plans`, `services`, `models`, `capabilities`, and `credit_packs` is `available`, `unavailable`, or `error`. A successful reader with zero rows establishes an empty section. An absent reader never does. Current/future separation uses the owning timestamp and half-open intervals. Existing clients retain the original response fields; older projections without coverage remain conservatively partial in the page.

Every section has its own reader. A real PostgreSQL reader error produces an explicit section error without discarding successful siblings. Failure to establish serving-hub availability fails the request. Closed or unconfigured hubs publish no rows and unavailable coverage. With every reader working the catalogue reports complete coverage, which says the readers answered, not that a hub has published anything.

Optional price disclosure is an allowlist of existing offer name/id, acceptance-text version and plan capacity. Plan payloads validate through `SubscriptionPlanVersionSchema` and must match the active row's id/version/offer/payer kind/exact active price. Existing immutable draft payloads retain `status: draft` after activation; the active row is the lifecycle authority. Malformed, mismatched, superseded or missing bindings produce an error, not a silently complete empty plan section. Public price reads do not load private billing account, provider cost, usage or staff columns.

The page shows free participation, coverage, stable section order, current and upcoming rows, explicit zero, unknown terms/tax/unit, and disabled sponsorship. Exact money uses `BigInt` plus `Intl` parts, without converting minor units to `Number`. No paid commitment is created here; booking authorization and acceptance remain in their owning commands. Public version details are informational, never an acceptance token.

## Model, capability and credit-pack sale versions

`price_sale_terms` adds what a `price_version` lacks for these kinds (ADR 010 decision 25, ADR 012 decision 33): the model or capability, the meter and how many units the amount buys, or a pack's credits, validity, expiry notice and refund policy version. No price or pack ships with the engine; amounts are the operator's settings.

- **Commands:** `POST /v1/admin/billing/sale-prices` drafts under `admin.commerce.price.draft`, creating the offer on first use. `POST .../:id/activate` needs `admin.commerce.price.activate` and a consumed `commerce.activate_price_version` approval for the exact digest, and the drafter cannot activate. An activation may name `supersedes`, the one earlier version it replaces. The approved digest binds that exact choice, so the same approval cannot be reused with or without it, and a draft's staff row lists the versions it may supersede with the digest for each. `GET` lists every version at the staff member's own hub, and `GET /v1/admin/billing/fees` does the same for fee versions, for the console (HUBC-009).
- **Supersession:** a signed end date never changes, so the replaced version's digest stays verifiable. `price_sale_supersession` records the replacement append-only, the old version moves to `superseded`, and its effective end is derived: public `effectiveTo` shows it, and `disclosure.supersededBy.signedEffectiveTo` keeps the signed end. It stays published until the new version starts. An audit row names the old version, its old end and its new end. A version with an end date cannot supersede one that runs beyond it (`billing.supersede_leaves_gap`), because the offer would have no price afterwards.
- **One price per subject:** two offers cannot price the same model or capability on the same meter in overlapping intervals (`billing.version_overlap`), under a lock taken after the offer's.
- **No way around it:** a trigger on `price_version` refuses to activate these kinds without their terms and the exact consumed approval, to change their end date, or to mark them superseded without the approved record, so the owner-run catalogue can do none of these.
- **Real subjects:** a model price must name a model the hub has a cost record or active route for, and a capability price a capability in a shipped manifest (`billing.sale_subject_unknown`). MODEL-001 will replace the model check with its catalogue. A cost record only proves the model exists: it never sets or changes a sale price (tested).
- **Credits never expire silently:** `validityDays: null` means no expiry; any expiry needs advance notice shorter than the validity, in the contract and in a database check.
- **Limits:** publishing a version charges nobody. AGT-004 owns metering, markup prices and consuming these versions; BILL-004 owns purchase, renewal and refund flows. An offer's name is inside every version's digest, so a later version cannot rename an offer.

## Referral programme terms

`referral_terms_version` holds the terms of a referral programme, versioned and disclosed like a fee (ADR 018; ADR 025 decision 21). Nothing here issues a reward: GROW-001 owns execution, and no programme, value or text ships with the engine.

- **Commands:** `POST /v1/admin/billing/referrals` drafts under `admin.growth.referrals.draft`; `POST .../:id/activate` needs `admin.growth.referrals.activate` and a consumed `growth.activate_referral_terms` approval for the exact digest; the drafter cannot activate and the approver differs from the requester. `POST .../:id/withdraw` stops a programme at once for the same permission and digest, audited, without a second person, because stopping protects participants. `GET` lists every version at the staff member's own hub. All routes need an elevated session; the hub comes from serving configuration, never the body.
- **Limits:** a reward is `platform_credit`, never cash, in the contract and in a database check. The draft names `legalReviewRef`, the counsel review of the terms; the approver's digest binds it, and it never reaches the public projection. Whether counsel approved is the operator's record, not something the engine can verify.
- **Disclosure:** activation needs the operator's terms in every hub language (`billing.language_missing`). `GET /v1/pricing` adds `referrals` and `coverage.sections.referrals`; an empty array with `available` means the hub runs no programme, and older responses without the field stay partial. A visitor in a language the hub does not publish sees the operator's text in a published language, labelled.
- **Immutability:** terms never change, drafts included; intervals are half-open, never back-dated and cannot overlap within a programme, under an advisory lock. Only lifecycle columns move, and only draft to active and active to withdrawn.
- **Human only:** activation runs under a staff elevation, which no agent principal holds; agents draft nothing here.

## Confirmation adapters

The internal `bookingFees` repository accepts only an existing immutable source scope. No HTTP command can manufacture a scope, choose participants or supply home hubs. A disclosure stores both public fee snapshots and its exact digest. The app-role SECURITY DEFINER binding command independently resolves the real destination: consultation scope IDs identify bookings, while task scope IDs identify offers and resolve through the actual agreement offer reference. It validates immutable digests, parties, recorded source hubs, lifecycle and fees before inserting either a binding or its audit event. Unsupported source kinds fail closed. Confirmation and binding recheck actor, home hub, source digest, active interval and original fee IDs. A successor never replaces an expired shown version. Binding is append-only and single-consumption; the owning acceptance transaction rolls it back on failure.

- **Consultations:** integrated only after CONS-001 PR #392 merged. New source provenance comes from creation through each server-configured hub. Proposals pin both fees in the existing immutable terms digest; buyer acceptance and seller confirmation bind the exact shown versions in the same transactions. Existing privacy, source-hub and mail-locking behavior remains in the owning module. Both the stored agreement and booking final transitions enforce the gate. Historical unbound rows are identified only by exact IDs and digests captured once by the migration; neither a legacy commission label, missing provenance, backdated timestamps nor hub configuration creates an exemption. Test fixtures seed this protected snapshot explicitly through their migrator connection; no runtime command can write it.
- **Tasks:** creation records request/offer provenance. `POST /v1/billing/fees/task-offers/:id/disclosures` returns an authorized immutable snapshot. Both existing acceptance commands require `feeConfirmation: { disclosureId, digest }` on the production adapter. The original task offer/request and `trustwork-digest-1` agreement digests remain unchanged; separate bindings record the disclosed fees. Buyer mandate/private ceilings include the fee; seller private floors use net proceeds. Generic task rates work; no taxonomy-to-fee-category mapping is invented. Database guards require both bindings before assignment. Historical task agreement IDs and digests use the same migration snapshot. The historical adapter lives only in tests and explicitly seeds that trusted fixture snapshot.
- **Tickets and courses:** no implemented owning booking/confirmation path exists on this base. The internal adapter and negative tests are present; no source scope means unavailable. There is no fabricated live ticket or course integration.
- **RFQ and quote orders:** no commission applies, by the conductor's ruling of 2026-11-03: the frozen `MarketplaceFeeKind` stands at its four kinds, `placeOrder` refuses a platform charge, and acceptance needs no fee disclosure. `tests/billing/fees/neutrality-scan.test.ts` pins this. Adding a commission here would need a new decision and a contract change, not a mapping onto an existing kind.
- **Federation:** tests exercise two actual configured hub applications sharing the test database, proving own-participant bindings. Remote signed-envelope ingestion is not implemented here and is not claimed proven.
