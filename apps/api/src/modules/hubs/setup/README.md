# Setup wizard backend (HUB-004)

The first run of a node ([setup wizard](../../../../../../docs/engine/hub-console/setup-wizard.md), [installation](../../../../../../docs/engine/hub-console/installation.md#the-setup-token)): a fresh node becomes a configured **draft hub** with one founding administrator. Storage and every rule are in [`packages/data/migrations/setup`](../../../../../../packages/data/migrations/setup) and [`repositories/setup.ts`](../../../../../../packages/data/src/repositories/setup.ts); contracts are the frozen `SETUP_STEPS`, `SetupStateSchema` and `nextSetupStep` of `hub.ts` plus the additive [`hub-setup.ts`](../../../../../../packages/contracts/src/hub-setup.ts). The wizard UI is `apps/web/app/admin/setup` (ADM-002 shell; live mode in `_live/`).

Status: **Live** as an API and wired wizard (not deployed). Tests: `tests/hubs/setup/*` on real PostgreSQL under the runtime role.

## The setup token

`DATABASE_URL=<migrator url> PUBLIC_ORIGIN=https://build.example.org npm run setup:token -w @trustwork/api` prints the wizard link once. The token is 32 random bytes (base64url); only its SHA-256 and an expiry (24 hours by default, at most seven days) are stored. Issuing again replaces the token (the old one stops working at once) and keeps the answers. Issuance is owner-run (a maintenance session): the API runtime role cannot issue a token. The token opens exactly one setup run; finishing invalidates it, and afterwards no token can be issued again (`setup.finished`), nor on a node whose staff were assigned another way. Every route carries the token in `X-Trustwork-Setup-Token`, never in an API path or query; an unknown, expired or used token is `404 access.not_found`.

## Steps

| Step | Route | Needs | What happens |
|---|---|---|---|
| any | `GET /v1/setup` | token | `SetupViewSchema`: state (resume at `state.current`), install checks, saved answers, operator screening, the founding administrator's masked address, the caller's session, the attestation status as the launch gate reads it (SANC-009 `currentStatus()`) |
| 1 `install_check` | `POST /v1/setup/steps/install_check` | token | Address (HTTPS or localhost), database role without row-level-security bypass, object storage probe (write, read, delete), worker heartbeat (warns until the worker publishes one), clock against the browser, secret key; a failed check blocks |
| 2 `node_identity` | `POST /v1/setup/steps/node_identity` | token | Node name, domain, jurisdiction (restricted refused) |
| 3 `hub_identity` | `POST /v1/setup/steps/hub_identity` | token | A country is required; starting point pack or generic profile; territories in that country, each checked at country, region and place level; name in every hub language; engine languages; currency; IANA time zone |
| 4 `operator` | `POST /v1/setup/steps/operator` | token | Legal entity, contacts, ownership declaration, the deployment-location statement (entity and hosting country and region, jurisdiction-gate mode; restricted places and missing regions refused); the operator is screened against the engine baseline lists (SANC-003 matcher; `not_screened` without a loaded baseline, labelled `fake` with `TRUSTWORK_SETUP_OPERATOR_SCREENING=fake`) |
| 5a `first_admin` | `POST /v1/setup/first-admin/account` | token | Records the address and signs up through BE-001 (verification mail through the outbox; on a node without live e-mail the worker's log transport shows the link) |
| 5b `first_admin` | `POST /v1/setup/first-admin` | token and the new account's session | The caller, with an active authenticator app and unused recovery codes (BE-004 shows the ten codes once), confirms "I have stored them" and becomes the founding administrator: `node-operator` at the node (released as version 1 when no definition exists, `setup_founding_permissions`). From now on every change also needs this person's session |
| 6 `storage_residency` | `POST /v1/setup/steps/storage_residency` | token and session | Where personal data is stored and processed, privacy regime |
| 7 `providers` | `POST /v1/setup/steps/providers` | token and session | Every capability fake, manual or "connect later"; language models later through OpenRouter (optional) or one direct provider. Nothing is connected |
| 8 `modes` | `POST /v1/setup/steps/modes` | token and session | Data mode and moderation; registration closed, indexing off, automation manual, module dependencies enforced |
| 9 `review` | `POST /v1/setup/finish` | token, session and a live elevation | One transaction as the founding administrator (below) |

Finishing refuses without a configured jurisdiction gate in this process (`jurisdiction_gate_unconfigured`) or with a different one than stated (`jurisdiction_gate_mismatch`); then it attests the deployment location through SANC-009's `attestation_attest` (unless the current attestation states exactly this and is in force), requires the attestation status `valid` or `renewal_due`, creates the hub with its territories and every launch gate through HUB-001's `hubs_create`, activates configuration version 1 of `identity` and `country` (CFG-001's deployment document, `source = deployment_import`) and `modes`, drafts `legal` (operator entity), `residency` and `providers` (sensitive domains: a second person activates them), and finishes: the database re-checks the founding administrator, the order, the second factor, an attestation in force and a draft hub, and invalidates the token. Every launch gate stays `open`; the console's checklist shows what remains. Of two simultaneous finishes one waits for the run's lock and then finds the setup finished.

The routes are not `@Idempotent`: each is a state transition that a retry repeats harmlessly (a step answer replaces itself; binding is idempotent for the same person) or refuses (a finished setup is not found).

## Decisions and limits

- **Founding role.** DATA-002 allows one founding assignment per person, so the founding administrator receives `node-operator` at the node only; a node assignment covers every hub of the node, which includes what `hub-owner` would give. The hub runs in reduced separation of duties until a second staff member joins (`two_staff_with_second_factor`).
- **The founding path in the database.** DATA-002's assignment guard accepted founding administrators only from a maintenance session, which the API runtime role can never be. The setup migration replaces `admin_assignment_guard` with the same function plus one path: the bootstrap row `setup_bootstrap_admin` inserts in the same transaction, for `node-operator` at node scope and the person the open run was just bound to. Every other rule is unchanged (integrator review).
- **The attestation is made when finishing**, not in step 4: SANC-009 binds it to an elevated staff session, and the only staff member is created in step 5. Step 4 records and checks the statement; the review shows its state.
- **Sensitive domains stay drafts.** `legal`, `residency` and `providers` are sensitive (`SENSITIVE_CONFIG_DOMAINS`): the database refuses to activate them without a second person, so the residency and the operator entity become active when the second staff member approves them; `data_residency_configured` and `operator_recorded_and_screened` stay open until then.
- **Not here yet.** The node signing key (generated in step 2 by the design) is KEYS-001's; passkeys (WebAuthn) are not implemented by BE-004, so only an authenticator app counts; the worker publishes no heartbeat yet; a potential operator match is recorded and keeps the gate open, but the operator entity is not a screening subject, so it does not enter the compliance review queue (SANC follow-up); the legal payload has no fields for the form, address, abuse contact and ownership declaration (they stay in the setup record; contract follow-up).
